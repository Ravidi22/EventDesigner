Eve.
Runtime architecture

Eve is a website. The confusing part is which half of it runs where.

There is no app to install and no second project called “the backend.” There is one repository that runs in two places at once — and right now, one of those two places is doing nothing at all. This page is what changes when we fix that.

Is it a website? Where does the code run today? What is “the server”? What happens when I save? What lives in the cloud? What gets deployed?
The delivery

Nothing is downloaded. The designer opens a URL.

On a desktop it is a browser tab. On the tablet at the venue it is the same browser tab. There is no installer, no app store, no update to push to anyone — you deploy, and the next time they load the page they have the new version.

That was settled before any code was written. ADR-1 in the architecture doc chose a browser app over a native desktop one for two reasons that still hold: the phase-2 client preview link needs a URL no matter what, and shipping a fix should be git push, not a support call.

Everything else on this page is about what sits behind that URL.

The honest starting point

Today there is no flow — because there is no server half yet.

This is why you cannot find the architecture: it isn't hiding. Every screen in Eve is marked "use client", every byte of data is in localStorage, and the Next.js server currently does one job — hand over the files and go back to sleep.

The schema in lib/db/schema.ts is complete and well-modelled, and nothing imports it at runtime. There are zero API routes. There is not a single "use server" in the codebase. The right-hand side of the picture below is the work we are about to do.

This is the real blocker, not a nicety. A design document is a business asset — the requirements doc says so (NFR-3). Right now one browser profile is the entire database, and the only backup that exists is the “download JSON” button in Settings. You cannot run a real client meeting on that.
The part that trips everyone

The backend is not another project. It is the files that don't say “use client”.

Next.js is one program that runs in two places. Every file is a server file by default — it executes in a Node process in the cloud, where the database password lives. Writing "use client" at the top of a file opts it into being sent to the browser as well, where clicks and drags happen and where nothing can be trusted.

So the boundary you have been looking for is not between two repositories. It runs through this one, and you can see it in a single feature.

Why the migration is small

Every storage call in Eve already goes through a lib/*/storage.ts module — no component anywhere touches localStorage directly. That was built on purpose, and it is the reason the backend is a per-module job rather than a rewrite: each of those files swaps its body from a browser write to a database write, and the twenty screens above them carry on unchanged.

What belongs outside the app

Three things get rented. Everything else stays in the monolith.

These three cannot live inside your Next.js app for the same underlying reason: a deploy platform runs your code on a machine that may be different next request and has no disk you can keep. Anything that must own storage or secrets has to be its own service.

Postgres

Neon

Events, catalog, venues, and the design documents as JSONB — the schema you already wrote.

Why outside: a database is a running program that owns a disk. Your app is given no disk it can keep.

File storage

Cloudflare R2

Gallery photos, product images, venue plan underlays — the entire visual half of the product.

Why outside: same disk problem, plus photos are big and need a CDN, not a trip through your Node process.

Auth

Clerk

Who is signed in, which studio they belong to — the check every server action starts with.

Why outside: password hashing, sessions, reset mail, 2FA. Every one is a security bug waiting to be written.

What must not be split off

Everything else. No separate API server, no queue, no “catalog service.” The architecture doc is explicit about this (ADR-6): one monolith on managed infrastructure. Splitting into services solves a problem of coordinating between teams — which, as one developer, you do not have. What it buys you instead is three deploys to debug rather than one.

The single exception that doc carved out — a background worker for heavy PDF vision processing — is now moot, since PDF import was dropped from the product and hall sketches are drawn in the app.

One order-of-work note

File storage unblocks more than it looks like: gallery photography, product images, and tracing a venue's real floor plan are all the same missing capability. The gallery is currently coloured tiles and PlanUnderlay is a type with no renderer — both are waiting on the same bucket.

The finished picture

Three things exist in production. You write one of them.

git push Vercel builds and hosts the Next.js app — both halves of it, one deployment yours
DATABASE_URL Neon hosts the Postgres instance ≈ $0–19 / mo
S3 credentials R2 hosts and serves the photos ≈ $0–5 / mo
CLERK_KEY Clerk handles sign-in and sessions free at this size

No servers to patch, no Docker in production. The docker-compose.yml in the repo only runs Postgres on your own machine while developing — it never ships.

The short version. It's a website. Next.js is both halves of it in one repository, split by a line — "use client" — that runs through the files rather than between projects. The canvas stays in the browser because it has to feel instant; the document goes to the server because it has to survive. And the only pieces that belong outside your app are the database, the file bucket, and the login provider, because all three need to own disk or secrets that a deploy platform will never hand to your code.
