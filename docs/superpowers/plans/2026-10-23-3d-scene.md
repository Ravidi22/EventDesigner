# 3D Scene Implementation Plan

> **Status 2026-10-23:** Phases A–D built on `feat/3d-scene` (A 2e7283c, B c566849, C+D and the first visual round after them). Migration 0022 (`event_scenes`, `scene_links`) is applied to `develop`; `npm run db:verify:scene` walks save → read → refuse → mint → open → count → revoke → expire → archive against it. The scene was SEEN for the first time on 2026-10-23 — headless Chromium (Playwright installed in the session scratchpad, software WebGL) rendering a copy of reference plan A through `/v/<token>` — and sharpened from the screenshots: image-based light, warm interior fill, neutral tone mapping, sheen fabric, polished tile, draped cloths with folds, bloom heads with per-head shade, real-size tapers, place settings, table close-ups that never stand in a wall, merged draw calls (1,364 → ~320), constant light count across moods, portrait field of view. **Not yet seen on a real GPU or a real phone** — the gates are still Ravid's.

> **For agentic workers:** execute task by task, in order; every task ends at its verify gate. Steps use checkbox (`- [ ]`) syntax for tracking. Spec of record: [2026-10-23-3d-scene-design.md](../specs/2026-10-23-3d-scene-design.md) — read §3 (the recipes) and §11 (the DECIDEs, built on the recommended answers) before any task.

**Goal:** A live, view-only 3D room built from the design document and the catalog's own fields, shown to the client as curated viewpoints and a guided tour — on a `/scene` tab, an optional meeting stage, the client portal and an expiring no-login link.

**Architecture:** `lib/scene/` is a pure builder (document + plan + catalog + settings → a list of bodies in plan mm, z up; self-checked, no three, no React). `components/scene/` is the one viewer that draws that list with three.js via react-three-fiber, lazy-loaded, rendering on demand. Four screens mount the viewer; none of them owns geometry. Camera state (viewpoints, tour, mood) is an `event_scenes` row, never part of the drawing.

**Tech Stack:** Next.js 16.2 (App Router, Turbopack), React 19.2, TypeScript, `three` 0.186, `@react-three/fiber` 9.8, `@react-three/drei` 10.7, drizzle/Postgres (Neon), Better Auth, Tailwind 4 tokens.

## Global Constraints

- **RTL / Hebrew-first.** DOM UI uses logical properties; all strings Hebrew. The WebGL canvas itself is direction-less; its bar is RTL like every other bar.
- **three.js stays in `components/scene/`.** No `from "three"` / `@react-three/*` anywhere else — `check:scene-boundary` (Task A1) fails the build otherwise. `lib/scene/` is plain TS.
- **The builder is pure and self-checked.** `buildScene` has no DOM, no fetch, no React; `npm run check:scene` builds the fixture document and asserts it. Everything the viewer draws comes from the builder; the viewer never reads the document.
- **No prices, ever.** `lib/scene`, `components/scene`, `app/(app)/scene` and `app/v` join `CLIENT_FACING` in `lib/suppliers/cost-boundary.ts` (Task A1). Client surfaces pass products through `clientProduct`.
- **The drawing is never written.** Nothing in this plan calls `saveDocument`, dispatches a document action or touches `design_documents`.
- **Lazy, client-only.** The viewer is imported with `next/dynamic(…, { ssr: false })` from a client component. three never reaches a server bundle or `/studio`.
- **Render on demand.** `frameloop="demand"`; `invalidate()` on camera moves, settings changes and document changes — never a render loop idling on a phone.
- **Verify gate (every task):** `npm run typecheck`, plus the task's own `check:*`. Phases end at a **browser gate** — Ravid opens it; nothing from the next phase starts before.
- **Branch:** `feat/3d-scene` off the current branch; other sessions share this checkout (stage only your hunks). Migrations via `db:generate` → `db:migrate` against `develop`, committed with their snapshot and journal.

## Task A2: The vocabulary — `types.ts` and `frame.ts`

**Interfaces (produces):**
```ts
export type Vec3 = { x: number; y: number; z: number };          // plan mm, +y down the plan, z up
export type Transform = { at: Vec3; rotationDeg: number; mirrored?: boolean; scale?: number };  // translate·rotate·mirror·scale, as the canvas
export type MaterialKind = "matte" | "fabric" | "gloss" | "glass" | "metal" | "water" | "foliage" | "emissive";
export interface MaterialRef { colour: string; kind: MaterialKind; texture?: Texture; image?: TextureImage; opacity?: number; tint?: string }
export type Part =
  | { shape: "box"; w: number; d: number; h: number; at: Vec3; rotDeg?: number; material?: MaterialRef }
  | { shape: "cylinder"; rTop: number; rBottom: number; h: number; at: Vec3; segments?: number; material?: MaterialRef }
  | { shape: "sphere"; r: number; at: Vec3; segments?: number; material?: MaterialRef }
  | { shape: "extrude"; outline: BuiltOutline; h: number; at: Vec3; material?: MaterialRef }      // +z from at.z, outline in the part frame
  | { shape: "lathe"; profile: { r: number; z: number }[]; at: Vec3; segments?: number; material?: MaterialRef }
  | { shape: "plane"; outline: BuiltOutline; at: Vec3; side?: "up" | "down" | "both"; material?: MaterialRef }
  | { shape: "ribbon"; path: Point[]; h: number; at: Vec3; pleatMm?: number; material?: MaterialRef }; // vertical, along its path
export type NodeTag = { type: "floor" | "wall" | "door" | "ceiling" | "ground" | "feature" | "table" | "cloth" | "chair" | "item" | "stage" | "deck" | "edge" | "skirt"; id?: string; label?: string };
export interface BodyNode { kind: "body"; id: string; parts: Part[]; material: MaterialRef; instances: Transform[]; tag: NodeTag; lod?: "near" | "far"; castShadow?: boolean }
export interface EmitterNode { kind: "emitter"; id: string; at: Vec3; radiusMm: number; colour: string; strength: number }
export interface LabelNode { kind: "label"; id: string; at: Vec3; text: string }                 // author mode only
export type SceneNode = BodyNode | EmitterNode | LabelNode;
export type Mood = "day" | "evening" | "night";
export interface Viewpoint { id: string; name: string; eye: Vec3; look: Vec3; fovDeg?: number }
export interface Tour { stops: { viewpointId: string; dwellMs: number; travelMs: number }[]; loop: boolean }
export interface SceneSettings { mood: Mood; viewpoints: Viewpoint[]; tour: Tour | null }
export interface Scene { nodes: SceneNode[]; bounds: Bounds; roofedMm: number | null; stats: { bodies: number; instances: number; emitters: number } }
export interface SceneInput { doc: DesignDocumentContent; plan: EventPlan; structure: VenueStructure /* arranged */; settings: SceneSettings; author: boolean }
```

## Costs (what this feature costs, in every currency)

**Money: ₪0 in new services for phases A–D.** three.js, react-three-fiber and drei are MIT; rendering is in the visitor's browser (ADR-6 holds: no worker, no render service, no second deployment); textures are drawn procedurally at runtime, so there are no texture assets to host; a designer's uploaded texture image is served by the existing file route (R2 charges no egress); two small Neon tables; the viewer is static JS on the CDN. The only costs that could ever appear are in phase E and all optional — MP4 transcoding if WebM is not enough, AI photoreal renders per image, paid 3D model packs.

**Effort: the biggest single feature since the sketch.** Rough new code: A ≈ 4 000 lines (the table recipes are most of it), B ≈ 3 500, C ≈ 1 800, D ≈ 1 200, plus fixtures and checks — about 10 000 lines over roughly 6–10 long sessions, with four browser/phone sessions of Ravid's (≈ 30 min each) as gates. Phase A alone is about one and a half client-side builds.

**Bundle and runtime, paid by the visitor:** ≈ 700 kB gzipped loaded only on `/scene`, the meeting's scene stage, the portal's scene page and `/v` (never on the studio); WebGL2 (every phone since ~2017); 100–250 MB of GPU memory on an אמרה-sized scene; battery during a tour. The on-demand frame loop keeps a still view at zero cost.

**Maintenance: a fourth renderer.** Every new `SymbolKind` or category needs a 3D function in `items.ts` from now on — the fallback box keeps the scene whole in the meantime (it degrades, never breaks), and because the builder reads the same geometry functions as the canvas and the printed map (`tableFootprint`, `dressingSpots`, `seatsAround`, `layStage`, `composeFlowers`, `barDrawing`), a rule changed in one place follows into 3D with no extra edit.

**Risk-cost:** the frame mapping and the look are unverifiable here; the first browser gate is the cheapest moment to be told "not like that", which is why phase A is small in scope (tables) and ends there.
